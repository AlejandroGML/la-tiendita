Tip

Litestar resuelve automáticamente los parámetros de función como dependencias inyectadas. async def list_products(self, product_service: ProductService) — Litestar instancia o reusa ProductService según su scope configurado (singleton por defecto). Cero boilerplate de DI.

Repositorios — CQRS ligero

Capa de acceso a datos con repository pattern + SQLAlchemy 2.x async. Para queries complejas (dashboard, catálogo con filtros), se usa CQRS ligero:

async def get_products_with_filters(
    self, session: AsyncSession, filters: ProductFilter

    stmt = select(Product).options(selectinload(Product.variants))
    if filters.search:

    if filters.category_slug:
        stmt = stmt.join(Product.category).where(
            Category.slug == filters.category_slug
        )
    # ... género, talla, material, condición, precio, stock, orden
    total = await self._count(session, stmt)
    stmt = stmt.offset(filters.offset).limit(filters.limit)
    result = await session.execute(stmt)
    return result.scalars().all(), total

Persistencia y Caché

PostgreSQL 16: datos relacionales + full-text search (tsvector con triggers automáticos). Alembic maneja migraciones que se aplican al iniciar la app.

Redis 7: cache-aside con TTL configurable por recurso (productos: 5 min, categorías: 30 min) + LRU eviction 512 MB. También funciona como broker de ARQ para background jobs.

Info

La invalidación de caché se dispara por event bus: cuando un producto se actualiza, product_service emite ProductUpdated, el handler de caché escucha e invalida las keys relevantes. Sin dependencias circulares.

Event Bus

Infraestructura de publicador/suscriptor en memoria para cross-cutting concerns. El bus es síncrono y en memoria (no Redis pub/sub) — decisión deliberada para este volumen.

Background Jobs — ARQ

ARQ (Async Redis Queue) ejecuta tareas fuera del ciclo request-response: procesamiento de imágenes, envío de emails transaccionales, cleanup de tokens expirados.

¿Por qué ARQ sobre Celery?

Este proyecto es async-first (Litestar + SQLAlchemy async). Celery requiere un thread pool separado para bridge sync/async. ARQ corre nativamente en el event loop de asyncio, solo necesita Redis (sin RabbitMQ), y el código de worker usa los mismos patrones async que la API. Para este tamaño de deploy, simplicidad gana.

Stripe

Integración con Stripe para pagos con tarjeta. El frontend crea PaymentIntent, Stripe Elements renderiza el formulario, y el webhook verifica firma, crea la orden, vacía carrito y envía email.

python · backend/app/services/stripe_service.py
async def create_payment_intent(
    self, amount_cents: int, cart_id: UUID
) -> dict:
    intent = stripe.PaymentIntent.create(
        amount=amount_cents,
        currency="eur",
        metadata={"cart_id": str(cart_id)},
    )
    return {"client_secret": intent.client_secret}
Peligro

El webhook de Stripe DEBE verificar la firma con stripe.Webhook.construct_event(). Sin verificación, cualquier persona puede enviar un POST falso marcando órdenes como pagadas. Este proyecto lo implementa correctamente.

Auth JWT con 2FA

El sistema usa rotación de tokens: access token expira en 15 minutos, refresh token en 7 días. El interceptor HTTP de Angular detecta 401, renueva con el refresh token, y re-intenta la petición original — transparente para el usuario.

Guards e Interceptors

typescript · guards e interceptors
// Interceptor HTTP: renueva access token automáticamente
intercept(req, next) {
  if (this.authService.isTokenExpired()) {
    return this.authService.refreshToken().pipe(
      switchMap(() => next.handle(this.addAuthHeader(req)))
    );
  }
  return next.handle(this.addAuthHeader(req));
}

// Guard de admin: verifica rol antes de lazy-load
canActivate(): boolean {
  if (!this.authService.isAdmin()) {
    this.router.navigate(['/']);
    return false;
  }
  return true;
}
05 / decisiones técnicas

El porqué importa tanto como el qué.

25 decisiones con fundamento concreto. Cada una con el qué, el por qué, y qué se rechazó. Organizadas en 5 categorías.

Arquitectura

Arquitectura hexagonal (ports & adapters)

¿Por qué?

Separar el dominio (services) de la infraestructura permite tres cosas: (1) los servicios se testean sin BD ni HTTP, (2) cambiar PostgreSQL toca solo repositories, (3) las reglas de negocio viven en UN lugar. Rechazado: MVC plano — la lógica se acumula en controllers/models creando acoplamiento.

Repository pattern y no ORM directo en services

¿Por qué?

Los services no saben SQL ni SQLAlchemy — solo hablan con interfaces de repositorio. Esto permite mockear repositorios en tests unitarios sin BD, centraliza queries (CQRS), y si mañana migro a MongoDB, solo cambio los repositorios.

Event bus en memoria y no message broker

¿Por qué?

Un broker (Redis pub/sub, RabbitMQ) añadiría complejidad operacional sin beneficio en este volumen. El bus síncrono ejecuta handlers en el mismo request. Si escala, migrar a Redis Streams es trivial porque los handlers ya están desacoplados.

Cache-aside y no write-through o write-back

¿Por qué?

Cache-aside es el más resiliente: si Redis cae, la app sigue funcionando (lee directo de BD). Write-through acopla escritura a Redis. Write-back puede perder datos. Cache-aside + invalidación por event bus da el balance correcto.

Tip de entrevista

La pregunta real no es "¿Litestar o FastAPI?" sino "¿por qué elegiste una alternativa menos popular?". Respuesta: Litestar eliminó 3 dependencias externas y ~200 líneas de boilerplate. El tradeoff aceptado: menos comunidad y documentación.

SQLAlchemy 2.x async

¿Por qué?

El ORM más maduro de Python (15+ años), soporte async nativo desde 2.0, permite mezclar ORM y SQL crudo (esencial para CQRS). SQLModel acopla modelo de BD a schema de API — viola separación de capas.

Pydantic v2 para DTOs

¿Por qué?

Escrito en Rust — valida 5-10x más rápido que v1. Define DTOs con tipos Python que Litestar usa para validación automática y generación de OpenAPI.

PostgreSQL 16

FactorPostgreSQL 16MySQL 8SQLite
Full-Text Searchtsvector nativo con rankingLimitadoFTS5 básico
JSON columnsJSONB con indexaciónSin indexación eficienteLimitado
ConcurrencyMVCCMVCC con gotchasSingle-writer lock

Redis 7 (cache + queue)

¿Por qué?

Redis hace dos trabajos: cache-aside con TTL configurable y broker de ARQ. Usar Memcached + RabbitMQ añadiría un servicio más que operar. Para este tamaño, un servicio que hace dos cosas > dos servicios especializados.

python-jose · PyOTP · bcrypt · Stripe

python-jose: soporta más algoritmos y está alineado con OAuth2/OIDC (roadmap Google OAuth). PyOTP: implementa TOTP/HOTP estándares (Google Authenticator). bcrypt: 25 años de batalla probada via passlib — argon2 queda como evolución si cambia el perfil de amenaza. Stripe: mejor documentación, SDK maduro, webhooks con firma criptográfica.

Frontend

Angular 22 y no React o Vue

¿Por qué?

Su estructura opinable (DI, módulos, guards, interceptores) fuerza una arquitectura consistente sin debates. Para 11 features con auth, formularios complejos y lazy loading, Angular da las herramientas nativas. React las requiere ensamblar de múltiples librerías.

Signals + RxJS y no NgRx · ngx-translate · Tailwind + PrimeUI

Signals + RxJS: NgRx añade 4 conceptos (actions, reducers, selectors, effects) y boilerplate. El estado es local por feature. Signals + BehaviorSubject cubren el 100% de casos. ngx-translate: carga JSON en runtime, permite cambiar idioma sin recargar (vs i18n nativo que compila un build por idioma). Tailwind + PrimeUI: Tailwind estructura, PrimeUI tematiza — semanas de CSS custom ahorradas.

Infraestructura

Docker multi-stage · Nginx reverse proxy · GitHub Actions

Docker multi-stage: separa build de runtime — imagen de ~150 MB vs ~800 MB. Menos superficie de ataque. Nginx: termination de TLS centralizado, sirve estáticos sin pasar por Python, rate limiting edge. GitHub Actions: nativo del repositorio, cero setup de infra, minutos gratuitos para open source.

Anti-patrones evitados

NO microservicios · NO GraphQL · NO event sourcing

Peligro: over-engineering

Para un proyecto de este tamaño, microservicios serían over-engineering: deployment de 8+ servicios, latencia de red, consistencia distribuida. La arquitectura hexagonal modular permite extraer un microservicio cuando se justifique — pero partir ahí es prematuro. GraphQL añade complejidad sin beneficio con un solo cliente. Event sourcing añade event store, proyecciones, snapshots — el audit log tradicional cubre el requisito a fracción del costo.

06 / infraestructura

Dev y prod, dos caras del mismo compose.

Docker Compose para ambos entornos. Multi-stage builds, Nginx reverse proxy en producción, ARQ worker como servicio separado.

yaml · docker-compose.yml (servicios principales)
services:
  postgres:
    image: postgres:16-alpine
    ports: ["5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

  api:
    build: ./backend
    ports: ["8000:8000"]
    depends_on: [postgres, redis]
    environment: {DATABASE_URL, REDIS_URL, STRIPE_KEY, JWT_SECRET}

  frontend:
    build: ./frontend
    ports: ["4200:4200"]
    depends_on: [api]

  worker:
    build: ./backend
    command: arq app.tasks.WorkerSettings
    depends_on: [redis, postgres]

En producción se agrega docker-compose.prod.yml que reemplaza el frontend dev por nginx:alpine sirviendo la SPA compilada, la API corre con uvicorn (no --reload), y el worker se ejecuta como servicio separado.

Lecciones aprendidas del testing E2E

Bug crítico

Los 3 JSON i18n tenían una coma faltante en la línea 192 — toda la app mostraba keys crudas. Hoy está validado en pre-commit.

Fix

Las fixtures E2E llamaban API sin prefijo /api/v1 → 404 silenciosos. El auth guard de Angular mantiene currentUser en memoria incluso tras borrar localStorage → los tests de redirect ahora usan browser.newContext() para sesión fresca.
