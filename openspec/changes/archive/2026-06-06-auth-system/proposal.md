# Proposal: Auth System

## Intent

Enable user authentication for La Tiendita. Without auth, carts are anonymous, orders have no owner, and admin features cannot be protected. This change introduces email/password registration and login, JWT token-based session management (access + refresh), Google OAuth2 sign-in, and role-based guards (user vs admin) — all prerequisite foundation for Change 3 (catalog) and every subsequent change.

## Scope

### In Scope
- User registration (email, password, name, preferred_lang)
- Login with email/password returning access + refresh tokens
- JWT access token (15m) + refresh token (7d) rotation
- Logout (revoke refresh token server-side)
- Google OAuth2 sign-in (redirect flow, backend exchange)
- Forgot/reset password with email token flow
- Role-based guards: `jwt_guard` (authenticated), `admin_guard` (admin role), `optional_auth` (attempt auth)
- Rate limiting on auth endpoints (in-memory, MVP-grade)
- i18n language detection middleware (`?lang=` + `Accept-Language`)
- Password hashing with bcrypt, refresh tokens hashed server-side
- Alembic autogenerate migration for `users` + `refresh_tokens` tables
- Angular 22 auth service, guards, and interceptors (functional `HttpInterceptorFn`)
- Login/register UI components with Google sign-in button
- Prerequisite tasks: venv creation, `pip install -e .`, `.env` file creation

### Out of Scope
- Email sending (password reset email is logged to console for MVP)
- Redis-based rate limiting (Change 7 — production hardening)
- Admin dashboard or user management UI (Change 7)
- Email verification flow (Change 7)
- Social auth beyond Google (left for future)
- Profile editing endpoint (Change 7)
- Persistent cart linking (Change 4)

## Capabilities

### New Capabilities
- `auth`: User registration, login, JWT token management, password reset, Google OAuth, role-based guards, rate limiting, i18n middleware

### Modified Capabilities
- `backend-core`: New config fields (JWT_ALGORITHM, ACCESS_TOKEN_EXPIRE_MINUTES, REFRESH_TOKEN_EXPIRE_DAYS, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET), controller/guard/middleware registration in main.py, engine model discovery for autogenerate
- `frontend-core`: New routes (/login, /register, /recuperar, /reset-password), route guards, HTTP interceptors, core services directory

## Approach

**Litestar native JWTAuth + httpx-oauth** (recommended by exploration). Leverages Litestar's built-in `litestar.contrib.jwt.JWTAuth` for access token validation and guard integration with OpenAPI auto-documentation. Refresh tokens are manual (hashed in DB). Google OAuth2 uses `httpx-oauth` for the server-side redirect flow. In-memory rate limiting via `defaultdict` (upgradable to Redis in Change 7).

**Frontend**: Angular 22 functional interceptors (`HttpInterceptorFn`) with `provideHttpClient(withInterceptors([...]))`. Lazy-loaded auth feature module. No class-based interceptors.

## Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Python 3.14 incompatibility with python-jose/bcrypt | Medium | Verified during pip install; fallback to manual JWT with PyJWT if jose fails |
| No .env file blocks app startup | High | Create `.env` as first apply task; app fails fast with clear error |
| Google OAuth untestable without credentials | High | Endpoints gracefully skip OAuth when GOOGLE_CLIENT_ID is empty; return 501 |
| In-memory rate limiter loses state on restart | Low | Documented as MVP tradeoff; upgrade path to Redis in Change 7 |
| Functional interceptors misconfigured (Angular 22) | Low | Verbatim pattern from Angular 17+ docs; class-based interceptors explicitly excluded |
| No test infrastructure exists | Medium | Include essential auth service unit tests with pytest in this change; defer guard/e2e tests |

## Rollback Plan

1. Revert the alembic migration: `alembic downgrade -1`
2. Revert `main.py` to remove controller/middleware/guard registration
3. Revert `config.py` to remove JWT/OAuth fields
4. Delete `.env` (recreated from template)
5. Delete `backend/app/{models,schemas,services,controllers,guards,middleware}/` auth files
6. Delete `frontend/src/app/{core,features/auth}/` auth files
7. Revert `app-routing-module.ts` and `app-module.ts` to pre-auth state

## Success Criteria

- [ ] `alembic upgrade head` creates `users` + `refresh_tokens` tables
- [ ] POST /auth/register returns access + refresh tokens, user persisted in DB
- [ ] POST /auth/login validates password hash, returns valid JWT
- [ ] POST /auth/refresh trades refresh token for new access token
- [ ] POST /auth/logout revokes refresh token server-side
- [ ] Protected endpoint returns 401 without valid JWT, 200 with valid JWT
- [ ] Admin-only endpoint returns 403 for non-admin users
- [ ] GET /auth/oauth/google returns 501 when GOOGLE_CLIENT_ID is empty (graceful degradation)
- [ ] Angular login page renders email/password form + Google button
- [ ] Angular auth guard redirects to /login when unauthenticated
- [ ] Angular auth interceptor attaches Bearer token to all requests
